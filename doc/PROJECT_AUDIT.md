# 智播豆项目审查报告

审查日期：2026-08-25

审查范围：`src/` Python 客户端、`android_agent/` 无障碍服务、`ut/` 测试脚本、scrcpy 音频链路、配置和构建文件。第三方二进制文件只核对版本与调用方式，没有进行逆向审计。

## 总体结论

当前版本可以启动，Python 源码能够通过语法编译，Android Agent 也能构建出 Debug APK；但在 VAD、消息发送、停止/重启并发、弹幕和配置持久化方面存在阻断无人值守直播的问题。正式发布前至少应完成本报告中 P0 项。

## 本轮修复状态

已修复本报告第 1～9 项：发送前开流与校准、WASAPI 端点优选、动态阈值与迟滞、分包语音累计确认、采集错误分流、轮次取消、scrcpy 强制音频、默认播放设备校验、VAD 配置保留，以及 Agent 成功响应兼容。音量表改为 Tk 主线程合并刷新并增加平滑峰值保持。第 10 项 ADB 兜底可靠性及 P1/P2 项仍保留在后续整改范围内。

### 运行日志复核（2026-08-25）

日志证明 `CABLE Output (VB-Audio Virtual Cable)` 的 WASAPI 输入已经收到豆包音频，出现过 `-9.9dB`、`-16.9dB`、`-19.0dB` 等明显高于 `-42dB` 阈值的峰值，并非完全没有音频。未进入 SPEAKING 的直接原因是旧状态机要求连续 0.3 秒逐帧越阈值，而 scrcpy/虚拟声卡分包之间夹有 `-100dB` 空帧，确认计时被反复清零。现改为 1.2 秒滚动窗口累计有效语音帧。

旧音量表从 VAD 工作线程每约 20ms 调用一次 `root.after()`，会堆积大量 Tk 回调；同时条宽仅使用瞬时原始帧，分包空隙的 `-100dB` 会立即清空刚出现的峰值。现改为工作线程只保存最新帧、Tk 主线程每 50ms 合并绘制，显示平滑值并保留短峰值；发送前校准阶段也会显示实时音量。

第二次运行日志已经验证 `WAITING → SPEAKING → ENDED → 下一条话术` 全链路成功。不过结束帧出现过“原始 `-43.9dB` 已恢复、5 帧平滑仍为 `-50.9dB`”的边界情况。结束检测现改为原始值或平滑值任一超过结束阈值即取消静音计时，避免声音恢复首帧被误判为播放结束。

## P0：阻断发布的问题

### 1. VAD 在消息发送后才初始化，丢失豆包开头语音

原流程先调用 `send_text_to_doubao()`，发送成功后才创建 `AudioPlaybackMonitor`。本机 PyAudio 初始化约需 2.7 秒，随后又读取 1 秒作为“静音基线”，因此状态机实际可能在消息发出 3～4 秒后才开始判断。短回复会被完整漏掉，长回复也会丢掉开头。

修复方向：发送前打开音频流并完成静音校准，发送后立即进入 WAITING/SPEAKING 状态机。

### 2. 发送后的音频被错误当作“静音基线”

`wait_for_doubao_speech_cycle()` 在消息已经发送后调用 `_measure_idle_floor()`。此时豆包可能已经开口，因此测到的是目标语音而不是环境底噪。该采样还会从输入缓冲中消费掉，后续状态机无法再看到。

修复方向：基线只能在发消息前测量；直播中只允许在确认上一轮已结束后重新校准。

### 3. 同名音频端点选择不稳定

当前电脑上 `CABLE Output` 同时对应 MME、DirectSound、WASAPI、WDM-KS 等多个 PortAudio 端点。原代码按设备名称长度选择，无法保证捕获到正确、低延迟且静音干净的端点。

修复方向：显式索引优先；名称匹配时优先 Windows WASAPI，其次系统默认端点，再次 DirectSound/MME；日志必须打印 Host API、采样率和最终索引。

### 4. VAD 使用固定阈值，基线只报警不参与判定

原阈值固定为 `-42 dBFS`，没有根据虚拟声卡增益或底噪调整，也没有开始/结束迟滞。不同电脑上会出现一直“说话中”或始终“未开口”。

修复方向：由静音基线和配置下限共同生成开始阈值，并使用更低的结束阈值形成迟滞；对高底噪路由直接判定为不健康。

### 5. 音频读取异常被当成真实静音

原 `get_current_rms_db()` 捕获任何异常后返回 `-100 dB`。设备切换、流断开或缓冲错误会启动静音计时，误切下一句。

修复方向：读取结果同时返回成功状态；连续读取失败应报告 `audio_error` 并停止自动轮播，不能当作静音。

### 6. 停止直播不能取消正在运行的 VAD

`stop_live()` 只修改广播标志，当前 VAD 仍可能运行到 45 秒超时。停止后立即重新开播时，旧线程可能再次把 `can_next_speak` 设为 True，造成两轮重叠发送。

修复方向：每次开播分配 generation ID 和 `threading.Event`；停止、关机和新一轮启动时取消旧监听，旧线程不得修改新一轮状态。

### 7. scrcpy 音频路由没有可靠验证

项目内置 scrcpy 4.1。该版本客户端使用 SDL 默认播放设备；仅设置 `SDL_AUDIO_DEVICE_NAME` 不能作为可靠的 Windows 端点选择保证。当前电脑恰好将 `CABLE Input` 设为默认播放设备，所以链路可能工作；默认设备改变后，VAD 会只收到静音。

另外 scrcpy 默认允许音频捕获失败后继续显示视频，界面正常并不代表存在音频流。

修复方向：启动前校验 Windows 默认播放设备是否与配置一致；增加 `--require-audio`，音频不可用时让启动明确失败。

### 8. 保存配置会丢失所有 VAD/音频字段

`settings.config.save_config()` 原先新建字典写盘，只保存界面字段，手工配置的 `vad_*`、`vad_input_device`、`scrcpy_audio_output_device` 会被删除并回落为默认值。

修复方向：在已加载配置上更新界面字段，保留高级音频字段；增加阈值、噪声余量和校准时长配置。

### 9. PC 与 Android Agent 的 HTTP 协议不一致

PC 端等待 `{"success": true}`，Android Agent 返回 `{"code": 0, "msg": "success"}`。Android 的 `/set_text` 实际执行“注入并发送”，PC 却判断失败并继续 ADB 降级，存在重复发送风险。

已修复：PC 端同时兼容 `success=true` 与 `code=0`，并按发送意图直接调用 `/inject_and_send`，不再在 Agent 成功后重复调用点击/ADB 兜底。

### 10. ADB 剪贴板降级会失败但返回成功

当前连接手机执行 `adb shell cmd clipboard help` 返回 `No shell command implementation.`。生产代码不检查命令返回值、输出、输入框内容或发送结果，仍直接返回成功，可能粘贴旧剪贴板并误发。

## P1：高优先级功能问题

- Android Agent 未限制前台包名，可能向其他 App 的输入框注入并点击。
- Android RPC 监听所有网络接口且没有鉴权；固定线程池中的连接也没有读取超时。
- Android Agent 找不到发送按钮时，只要写入成功也会向 PC 返回成功。
- 弹幕 WebSocket 循环从未启动，`state.live_running` 从未置为 True。
- 人数区间 `r1/r2/r3` 没有参与策略，直播始终固定循环 cmd1、cmd2、cmd3。
- “外音/内录模式”按钮只改变文案，没有改变发送或 TTS 链路。
- 抓屏结果没有保存或分析，每秒截图后立即丢弃。
- 开机自检判断 `mode == "online"`，实际状态检查只返回 `auto/offline`，对应检查永远不执行。
- 多设备场景没有贯穿使用 `device_serial`，ADB 可能操作错误设备。
- `core.state.__getattr__()` 对任意缺失变量返回 False，会隐藏变量拼写和状态遗漏。
- scrcpy 启动探测和 PyAudio 枚举可能阻塞 GUI 主线程数秒。

## P2：安全、质量和维护问题

- 授权检查恒为通过，管理员默认密码硬编码，密码摘要使用 MD5 且提交到 Git。
- README 仍为占位模板，缺少安装、音频路由、手机版本和故障排查说明。
- 依赖只有最低版本，没有锁文件和兼容版本上限。
- 没有 pytest、ruff、类型检查和 CI。
- `ut/*_test.py` 是导入即执行的真机脚本，不是隔离单元测试；测试收集可能直接发送消息、点击手机并生成截图。
- 部分 E2E 脚本仍导入重构前已经删除的函数，无法作为当前代码的回归保障。
- 大量 `except Exception: pass` 会吞掉真实故障，日志无法定位根因。

## VAD 验收标准

修复后的链路至少应满足：

1. 点击正式开播后，第一条消息发送前音频设备已经打开并完成静音校准。
2. 豆包思考期间保持 WAITING，不因静音切句。
3. 连续真实语音达到确认时间后进入 SPEAKING。
4. 说话中的短停顿不会切句；连续静音达到配置值后进入 ENDED 并只放行一次下一句。
5. 音频断流、设备错误和路由不健康时停止自动轮播，不得当作静音继续发送。
6. 点击停止或关闭总电源后，当前 VAD 在一个音频帧周期内取消，旧线程不能影响下次开播。
7. 同名 VB-Cable 端点优先选择 WASAPI，并可通过精确索引覆盖。
8. 保存普通配置后，高级 VAD/音频配置仍然存在。
